CJ Direct Device Path

Two WHCJ doors bypass the Artemis server entirely: the scheduler reads the FR terminals over ISAPI and walks each device's own gap-free event counter. Every step below is what the code actually does — main.run_device_cycle and device_events.py.

why it is safe to switch

Both mappings were confirmed by parity, not assumption: the device's own log and the Artemis door/events API returned identical (employee_no, timestamp) sets — 1457 events over 3 days, zero one-sided. The doorIndexCode column is kept only for that cross-check.

the premise

A counter can prove completeness; a clock cannot

Artemis window path

Asks “what happened between 08:00 and 08:30?”. If a terminal uploaded late, the window that would have carried the event has already closed. A missing event and a quiet half-hour look identical — the loss is invisible, and nothing records that it happened.

Device path

Asks “give me serial 134500 through 134511”. The device answers with a count, and the count is checkable against the width of the span. A hole becomes a number instead of an inference — and a poller that was down just asks for a wider span.

The query must be unfiltered (major:0, minor:0) because the completeness check needs the dense counter — every event type shares it. Asking the device for authentications only would return 14 of a 41-wide span every time, making the comparison meaningless. So major 5 / minor 75 is filtered in-process, after the check.

One poll, gate by gate

Called once per device by run_devices(), which holds the cross-process send lock (state/rymnet_send.lock) around the whole sweep so device and Artemis senders never overlap. Inside the scheduler this runs every DEVICE_POLL_SECONDS while it sleeps toward the next half-hour boundary — the two paths keep independent cadences.

cursor

Highest serial fully processed. The single source of truth for where a device resumes — which is also why a backfill is a state edit, not a flag.

last_sent

Dedup memory carried across cycles. Device polls are short and frequent, so without persisting it two events seconds apart either side of a cycle boundary would both pass the gap check. Aged against the newest event seen, not the wall clock, so a backfill of old serials still dedups correctly within itself.

Note the state directory is currently empty — neither device has a cursor yet. The next device run bootstraps each one at its newest serial and sends nothing.

the one real backstop

Device retention is the only copy. A device offline long enough for its event log to wrap loses that data outright — there is nothing upstream to re-ask. Depth is generous (~8 months observed), so cursor lag is the practical thing to watch.

two documentation drifts worth fixing

MIN_GAP_MINUTES is 1 in main.py:46, but the README says 5 in two places. And the README documents ex_view.py and ex_device.py — the read-only device viewers referenced by the backfill and gap-recovery flows — but neither file exists in the repo or in git.

Rymnet-side dedupe is the only guard against double-counting, so pick a backfill serial deliberately. And stop the service before manual sends: the cross-process lock will make them wait anyway, but stopping avoids contention on a long run.
